# 범위 결정 기록

시트를 대체하는 일을 시작하기 전에, 되돌리기 어려운 것들을 먼저 정한다.
각 항목은 **무엇을 정했는지**와 **왜 그렇게 정했는지**, 그리고 **나중에 바꾸려면
무엇을 치러야 하는지**를 함께 적는다.

이 문서는 구현 방법을 적지 않는다. 방법은 티켓과 설계 문서가 맡는다.

---

## 1. 클랜은 하나로 시작한다

미니언즈(`#2C8L822LQ`) 하나만 다룬다.

**다만 서버는 능력을 열어 둔다.** `GET /api/v1/clans` 는 목록을 돌려주고 표는
여러 줄을 담을 수 있다. 화면이 하나만 보여 주는 것은 화면의 선택이다.

> 백엔드는 기능을 열어 둔 것이고, 실제로 보여지고 표현되는 건 FE나 기획의 관점.
> 추후에 저 기능을 제공할 수 있으니 어떻게 사용할지는 나중에 결정한다.
> — 2026-09-14

**왜 이 방향인가.** 서버를 나중에 넓히려면 배포를 기다려야 하는데 화면은 그것을
기다릴 수 없다. 반대로 좁히는 것은 마이그레이션이 든다. 넓게 열어 두고 화면이
골라 쓰는 편이 양쪽 모두 싸다.

**바꾸려면.** 화면에 클랜 고르는 자리를 더하면 된다. 서버는 손대지 않는다.

## 2. 계정 중심으로 관리한다

`clan_members` 의 한 줄은 **게임 계정 하나**다. 사람이 아니다.

지금 클랜에 한 사람이 계정을 여럿 쓰는 경우가 **실제로 있다.** 그래서 언젠가
사람과 계정을 나눠야 하지만, 지금은 나누지 않는다.

> 등급을 사람에게, 사람과 계정을 나중에는 나눠야 할 것 같다. 지금은 계정 중심으로
> 먼저 설계. 사람으로 분리하려면 사람에 대한 계정 로그인이나 사람 관리가 더
> 필요하니까. — 2026-09-14

**왜 미루는가.** 사람을 다루려면 "이 계정이 누구 것인가"를 누군가 정해야 하고,
그러려면 로그인과 사용자 관리가 먼저 있어야 한다. 그것 없이 사람 표를 만들면
채울 방법이 없다.

**바꾸려면.** `users` 표와 계정을 잇는 열이 필요하고, 등급을 계정에서 사람으로
옮겨야 한다. 그때 점수를 합칠지 따로 셀지도 정해야 한다.

**지금 지킬 것.** 등급·점수·명단을 모두 계정 단위로 다룬다. "한 사람이 두 번
뽑히면 안 된다" 같은 규칙을 지금 넣지 않는다. 넣으면 계정 중심 설계에 사람
개념이 섞여 나중에 걷어내기 어렵다.

## 3. 등급은 둘이 사람 몫, 둘이 계산 결과다

시트가 쓰는 네 가지를 뜯어보니 성격이 둘로 갈린다.

| 등급 | 누가 정하나 | 언제 바뀌나 |
|---|---|---|
| **확정 ●** | 사람이 — 명예·길드장·부길드장 | 거의 안 바뀐다 |
| **제외 ✕** | 사람이 — 부캐, 쉬는 계정 | 거의 안 바뀐다 |
| **경쟁 △** | 나머지 전부 | — |
| **예비 ◎** | 점수 순위가 — 30위 밖으로 밀린 사람 | **매달** |

> 확정이라는 곳에는 명예나 길드장 부길드장은 거의 예외 없이 확정이야. 그 외는
> 다 경쟁이고 30 순위 벗어나게 되면 예비로 빠지게 되지. 제외는 부캐나 아니면
> 쉬는 계정은 안 넣는다. 등급은 점수표로 결정.
> — 2026-09-14

**이것이 지금 사이트와 가장 크게 다른 곳이다.** 사이트는 `config/clan.yaml` 에
정예·제외를 적어 두고 나머지를 일반으로 둔다. **"예비"가 계산 결과로 나온다는
개념이 아예 없다.** 등급을 전부 사람이 붙이는 꼬리표로 다루고 있다.

고쳐야 할 모양은 이렇다.

```
사람이 정하는 것   확정 ● · 제외 ✕          → 저장한다
계산되는 것        경쟁 △ · 예비 ◎          → 점수표에서 나온다
```

**바꾸려면.** 저장하는 값에서 경쟁·예비를 빼고, 점수를 낼 때 순위로 가른다.
지금 `clan.yaml` 의 `elite` 가 확정에, `excluded` 가 제외에 해당한다.

**아직 애매한 것.** "거의"라고 한 두 곳이다. 확정에 예외가 있는지, 30위 밖인데
예비가 아닌 경우가 있는지는 정하지 않았다. 실제로 만들 때 부딪히면 그때 정한다.

## 4. 원본은 API 하나다

`CoC API → D1 → REST API → 화면` 이 유일한 길이다. `data/clan.json` 과
`data/wars/` 는 걷어낼 것이며, 그때까지만 남아 있는 과도기 산물이다.

> 이제는 원본이 CoC API → DB 이런 순이니까 API가 원본이 될 수 있게끔 해 줘.
> clan.json 이런 방식은 걷어낼 예정. — 2026-09-14

**지금 원본이 둘이라 실제로 어긋나고 있다.** 클랜원 화면이 두 곳에 있는데
자료 출처가 다르다.

| | 월별 페이지의 "길드원" 탭 | `/members/` |
|---|---|---|
| 자료 | `data/clan.json` | D1 |
| 갱신 | 30분마다 자동 | 손으로 넣은 날에 멈춤 |
| 정렬 | 역할 순 → 트로피 순 | 이름 순 |

시간이 갈수록 같은 사람의 트로피가 두 곳에서 다르게 보인다. 보는 사람은 어느
쪽을 믿어야 할지 알 수 없다.

**왜 이렇게 됐나.** v0.6 에서 "클랜원 조회를 스펙부터 화면까지 이어 보자"고 새
길을 뚫으면서 옛 길을 걷어내지 않았다. 한 페이지씩 옮기는 방식이라 과도기에는
둘이 공존하지만, **옮긴 페이지의 옛 판은 그때 지워야 한다.**

**화면을 그릴 때 지킬 것.** "API가 원본"이라는 전제로 그린다. 옛 길에 맞춰
그리면 나중에 다시 그려야 한다.

## 5. 화면은 여섯으로 고정한다

시트 탭 하나가 화면 하나다. 시트를 쓰던 사람이 그대로 옮겨 올 수 있게 이름과
열을 맞췄다. **이 여섯이 구현 기준이며, 바꾸려면 이 문서를 먼저 고친다.**

| 보는 사람 | 화면 | 시트에서 온 곳 |
|---|---|---|
| 누구나 | **클랜원 인원** | 클랜인원관리 |
| 누구나 | **월별 점수** | [자동]월별점수 + [자동]월별 명단 조회 |
| 누구나 | **리그전 명단** | [자동]리그전 명단(월별) |
| 운영진 | **등급** | 클랜인원관리 E열 |
| 운영진 | **규칙** | 리그전 명단 탭의 커트라인 칸 |
| 운영진 | **보상 추첨** | 시트에 없음 |

시안: `docs/design/2026-09-14-screens.html`, `docs/design/2026-09-14-admin.html`

### 시트와 달라진 곳

- **두 탭을 합쳤다.** [자동]월별점수와 [자동]월별 명단 조회가 같은 일을 한다 —
  달을 골라 그 달 점수를 보는 것이다. 시트에서 나뉜 것은 수식을 짜다 보니
  그렇게 된 것으로 보인다.
- **[자동]리그전 명단(이전버전)은 옮기지 않는다.** 옛것이다.
- **보는 화면과 고치는 화면을 갈랐다.** 시트는 클랜인원관리 한 탭에서 보고
  고치지만, 사이트는 사용자 셋이 보기만 하고 바꾸는 일은 전부 운영자 화면에서
  한다.

### 화면에서 지킬 것

- **기간은 셀렉트 하나로 고른다.** `2026 / 09` 한 칸이다. 칩을 늘어놓으면 몇 해
  뒤에 줄바꿈이 나고 가로 스크롤이 생긴다.
- **등급은 확정·제외만 고를 수 있다.** 경쟁과 예비는 점수 순위가 정하므로 아예
  고르지 못하게 둔다. 아무것도 안 매기면 경쟁이다. 3번에서 정한 것을 화면에서도
  지킨다.
- **추첨 대상자를 손으로 고르지 않는다.** 리그전 명단에서 그대로 가져온다.
- **뽑은 결과에 날짜·뽑은 사람·그때 후보를 함께 남긴다.** 나중에 "왜 저 사람이
  됐나"를 따질 수 있어야 한다.

## 6. 등급은 현재 값 하나다. 달마다 쌓지 않는다

> 자 그러면 잠시만 리그전 명단 기록이 관리가되면 저정보를 채울수잇는정보겟네
> — 2026-09-14

등급은 **"지금 이 사람을 어떻게 볼 것인가"** 이지 **"5월의 등급"** 이 아니다.
부캐라서 제외인 사람은 5월에도 6월에도 제외다. 매달 다시 적는 값이 아니다.

| | 월별 점수 | 등급 |
|---|---|---|
| 언제 바뀌나 | 매달 반드시 새 값 | 사정이 생겼을 때만 |
| 저장 모양 | `(month, tag)` 복합 키 | 클랜원 한 명당 한 행 |

**그러면 과거 달의 등급은 누가 아는가.** 리그전 명단 기록이 안다. 선발을
확정하는 순간 그 달 명단을 남기면서 **그때의 등급과 순위를 함께 적는다.**
명단만 적으면 안 된다. 제외 ✕ 로 빠진 사람과 31위로 밀린 예비 ◎ 가 똑같이
"명단에 없음"으로 보이기 때문이다.

```
clan_members.grade   지금 이 사람을 어떻게 볼 것인가   ← 클랜원 티켓
league_rosters       그 달에 실제로 어땠는가          ← 리그전 티켓
```

**바꾸려면.** `member_grades(month, member_id, grade)` 같은 월별 표를 만들면
된다. 대신 등급이 안 바뀐 달도 49행씩 쌓이고, "이번 달 등급"을 물을 때마다
최신 달을 찾는 규칙을 코드에 또 넣어야 한다.

## 7. 응답은 덩어리로 나누고 부르는 쪽이 고른다

> BE 관점에서는 이게 필수는 아니다 (…) 만약에 우리 DB값만 원하는거면 DB것만
> 요청할수잇게금 해주는게 좋아보이고 coc api를 호출해야하지만 나타날수잇는건
> 구분햇으면 좋겟다
> — 2026-09-14

`Member` 하나에 성격이 다른 셋이 뭉쳐 있었다. 갈라서 `includes` 로 고르게 한다.

| 덩어리 | 무엇 | 비용 |
|---|---|---|
| 기본 | 우리가 주인인 값 — 식별자·표기·상태·경고·메모·시각 | DB 한 행 읽기 |
| `profile` | CoC 가 주인인 값 — 이름·직책·홀·트로피·기부 | **CoC 호출** |
| `league` | 리그전 선발 — 이번 달 점수·순위·등급 | 점수표 조회 + 순위 계산 |

**`include` 어휘는 `profile` 과 `league` 둘이다.** 늘리려면 이 줄을 먼저 고친다.

```
GET /api/v1/members                                  우리 값만. 가장 싸다
GET /api/v1/members?include=profile                  + CoC 현황
GET /api/v1/members?include=profile,league           + 이번 달 성적
```

**매개변수 이름은 단수 `include` 다.** JSON:API 가 그렇게 정했고 Stripe·Atlassian
은 `expand` 를 쓴다. 값이 여럿이어도 이름은 단수로 두는 것이 관례다.

**`league` 는 늘 이번 달이다.** 지난 달을 고르는 방법은 아직 정하지 않았다.
응답에 `month` 를 함께 실어 어느 달 값인지 밝힌다. 달이 바뀌는 순간 화면이
무엇을 보고 있는지 알아야 하기 때문이다.

**이름과 직책도 `profile` 로 내렸다.** 둘 다 CoC 가 주인이기 때문이다.

**부르지 않은 덩어리는 키 자체가 없다.** `null` 로 채우지 않는다. 묻지 않은
것과 값이 없는 것은 다르기 때문이다.

**`profile` 은 우리 DB 에 없다.** 부를 때마다 CoC 에 묻는다. 10번에서 정한
대로다.

**`league` 는 아직 열거형에 없다.** `monthly_scores` 가 비어 있어 항상 빈 값이
나온다. 없는 것을 스펙이 약속하면 부르는 쪽이 있다고 믿는다. 클랜전 기록이
들어오는 티켓에서 더한다.

**왜 `league` 라는 이름인가.** 점수·순위·등급·선발 명단은 따로 떨어진 넷이
아니라 한 가지 일의 네 단계다. 점수를 매기는 것은 순위를 내려고, 순위를 내는
것은 등급을 가르려고, 등급을 가르는 것은 30인을 뽑으려고 하는 일이다. 목적이
하나라서 도메인도 하나다. `rank` 라고 부르면 가운데 한 단계가 전체를 대표하게
되고, "선발 명단은 어느 도메인이냐"는 물음에 답이 궁색해진다.

```
packages/core/src/coc_core/
├── member/     누가 우리 관리 대상인가
├── clan/       우리가 다루는 클랜은 어디인가
└── league/     리그전 선발 — 점수·순위·등급·명단      ← 앞으로 생길 곳
```

기존 `coc_core/scoring.py` 는 점수 규칙(몇 별에 몇 점)이고 순수 계산이라 그대로
둔다. `league` 가 그것을 불러 쓴다.

## 8. 등급은 사람이 고치지 않는다

> grade 같은경우에는 우리가 수정하지 않는다 일단은 이건 점수에따라 정해지는거니까
> 수동으로 계산하는건 추후에 생각
> — 2026-09-14

네 등급 가운데 점수로 갈리는 것은 둘뿐이지만, **지금은 수동 입력 경로를 만들지
않는다.** 등급은 그달 점수가 정하는 값으로 다루고, 수동 예외는 나중에 정한다.

| 등급 | 점수로 계산되나 |
|---|---|
| 경쟁 △ | ○ 그달 점수 30위 안 |
| 예비 ◎ | ○ 그달 점수 30위 밖 |
| 확정 ● | ✕ 길드장·부길드장·명예 |
| 제외 ✕ | ✕ 부캐, 쉬는 계정 |

**따라서 이번 범위에서 `grade` 는 응답에도 `PATCH` 에도 없다.** `league` 덩어리가
계산 결과로 내려 줄 것이며, 아래 둘의 수동 예외는 그때 함께 정한다.

`clan_members.grade` 열과 도메인의 `MemberGrade` 는 남겨 둔다. 수동 예외가 들어올
자리이고, 아직 배포하지 않은 마이그레이션을 되감는 것보다 위험이 적다.

## 9. display_name 은 사람이 고치기 전까지 비어 있다

> display_name을 우리가 db값까지 채우지않는다 이건 fe 비즈니스 왜냐하면 이걸로
> 동기화때 누가 고친건지 모를수잇어서 사용자가 수정안한거면 null로 준다
> — 2026-09-14

```
display_name   사람이 정한 표기. 아무도 고치지 않았으면 NULL
name           CoC 가 지금 들고 있는 이름. 동기화가 늘 덮는다
```

**동기화는 `display_name` 을 채우지 않는다.** 채우면 그 값이 사람이 정한 것인지
동기화가 써 넣은 것인지 나중에 구분할 수 없다.

**비었을 때 무엇을 보여줄지는 화면이 정한다.** 서버는 "사람이 정한 표기가
없다"는 사실만 내보낸다. 화면은 `displayName ?? profile.name` 으로 대신한다.
그래서 이름을 보여주려는 화면은 `includes=profile` 을 함께 불러야 한다.

**`clans.display_name` 은 다르게 되어 있다.** 첫 동기화 때 CoC 이름으로 채우도록
적혀 있고 이미 값이 들어 있다. 클랜은 하나뿐이라 당장 문제가 되지 않지만,
규칙이 두 벌인 것은 사실이다. 언젠가 맞춰야 한다.

## 10. 클랜원 표는 CoC 에 물을 열쇠만 든다

> 원본은 coc 라고 말했던 것 같고 우리는 member 를 조회할 수 있는 키만 가지고
> 있자고 내가 요청했던 것 같아
> — 2026-09-15

`clans` 가 이미 지키는 규칙을 `clan_members` 에도 적용한다. 사본을 들면 두
곳에서 관리하게 되고 언젠가 어긋난다.

```sql
CREATE TABLE clan_members (
  id, external_id, display_name, status,
  warnings, description, created_at, updated_at, synced_at
);
```

**빠진 것.** `name`, `role`, `townhall`, `trophies`, `donations`,
`donations_received`

### 이름조차 담지 않는 까닭

계정이 삭제되면 CoC 가 404 를 준다. 그때 이름을 되찾을 길이 없다. 그러나
**과거 기록이 제 이름을 들고 있다.**

```sql
war_members(war_id, tag, name, townhall)   그 클랜전 시점의 이름
monthly_scores(month, tag, name, ...)      그달의 이름
```

5월 점수표는 5월의 이름으로 읽힌다. 이름은 그 기록에 속한 것이지 클랜원 표에
속한 것이 아니다. 아무 기록도 없는 사람이 계정을 지웠다면 우리가 아는 것은
태그뿐이며, 없는 이름을 지어내지 않는다.

`last_known_name` 같은 열을 두는 안을 한 번 냈다가 물렸다. 사본을 이름만 바꿔
남기는 것이었다.

### 동기화가 하는 일이 줄었다

| | 전 | 후 |
|---|---|---|
| 처음 보는 사람 | 등록 | 등록 |
| 사라진 사람 | INACTIVE | INACTIVE |
| 이름·직책·트로피 | **매번 덮어씀** | **하지 않음** |

### 탈퇴는 둘로 갈린다

실제로 CoC 에 물어 확인했다.

```
GET /players/{tag} → 200, clan 이 미니언즈    재적
GET /players/{tag} → 200, clan 이 없거나 다름  클랜 탈퇴. 계정은 살아 있다
GET /players/{tag} → 404                      계정이 사라졌다
```

우리 `status` 가 가리는 것은 **클랜 탈퇴**뿐이다. 동기화는 "클랜 명단에 없다"만
볼 수 있다.

### 목록과 단건이 묻는 방법이 다르다

| | 어디에 | 호출 |
|---|---|---|
| 목록 | `GET /clans/{clanTag}` | 전체에 **1번**. 클랜에 없는 사람은 `profile: null` |
| 단건 | `GET /players/{playerTag}` | 그 한 명만. 나간 사람도 나온다 |

목록에서 나간 사람마다 `/players` 를 부르면 호출이 사람 수만큼 늘고 Workers 의
하위 요청 한도에 걸린다. 한 명의 현황이 정확히 필요하면 단건으로 묻는다.

### 이름순 정렬을 서버가 못 한다

이름이 없으므로 처음 본 순서로 돌려준다. 표기와 CoC 이름 가운데 무엇으로 줄
세울지는 화면이 정할 일이다.

**바꾸려면.** 사본을 되살리면 된다. 대신 두 곳에서 관리하게 되고, 30분마다 도는
동기화와 화면이 보는 값이 어긋나기 시작한다.
