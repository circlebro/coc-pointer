# coc-pointer 설계 문서

작성일: 2026-09-07
상태: 승인됨 (2026-09-07, 사용자 검토 완료)

## 1. 목적

클래시 오브 클랜(CoC) 클랜의 **클랜 리그전 30인 선발**을 위해, 클랜원별 클랜전 활동 점수를 자동으로 집계하고 웹 페이지로 공개한다. 지금까지 월별 엑셀 파일로 손으로 관리하던 3단계(클랜전별 입력표 → 월 단위 점수표 → 최종 선발 명단)를 그대로 자동화하는 것이 목표다.

첫 버전의 범위는 다음과 같다.

- 일반 클랜전과 리그전(CWL) 결과를 CoC 공식 API에서 자동 수집한다.
- 엑셀과 동일한 공식으로 월별 점수와 30인 선발 명단을 계산한다.
- 결과를 정적 웹 페이지(GitHub Pages)로 공개한다.
- 현재 클랜원 목록(플레이어 태그 포함)을 함께 공개해, 관리자가 설정 파일에 넣을 태그를 바로 찾을 수 있게 한다.
- 관리자 설정(정예 멤버, 부캐, 제외, 경고)은 저장소 안의 설정 파일로 관리한다.

첫 버전에서 하지 않는 것:

- 서버, 데이터베이스, 로그인 화면 (GitHub 로그인이 관리자 인증을 대신한다)
- 과거 엑셀 데이터 가져오기
- 표 정렬/검색 같은 화면 상호작용
- 기부, 클랜 게임, 캐피탈 등 클랜전 이외의 활동 점수

## 2. 전체 구조

세 개의 독립된 조각으로 나눈다. 각 조각은 앞 조각이 만든 파일만 읽는다.

```
CoC API ──(RoyaleAPI 프록시)──▶ [수집기 collect] ──▶ data/wars/*.json
                                                        │
                                   config/clan.yaml ────┤
                                                        ▼
                                                 [계산기 scoring]
                                                        │
                                                        ▼
                                                 [렌더러 render] ──▶ site/ ──▶ GitHub Pages
```

실행 환경은 **GitHub Actions**다. 30분마다 자동으로, 그리고 Actions 탭의 "Run workflow" 버튼으로 수동으로 실행된다. 별도 서버는 없다. 저장소 자체가 데이터베이스 역할을 하며, 모든 클랜전 기록이 git 이력으로 남는다.

### 2.1 수집기 (collect)

- CoC 공식 API를 RoyaleAPI 프록시(`https://cocproxy.royaleapi.dev`)를 거쳐 호출한다. 프록시를 쓰는 이유는 API 토큰이 IP에 묶이기 때문이며, 프록시의 고정 IP(`45.79.218.79`)를 토큰에 등록하면 GitHub Actions처럼 IP가 바뀌는 환경에서도 동작한다.
- 프록시 앞단(Cloudflare)은 일반적인 `User-Agent` 헤더가 없는 요청을 403으로 거부한다(파이썬 기본 값이 차단됨을 확인). 클라이언트는 `User-Agent: coc-pointer/<버전>`을 항상 붙인다.
- 호출하는 엔드포인트:
  - `GET /v1/clans/{clanTag}`: 클랜 정보와 현재 멤버 목록. 매 실행마다 `data/clan.json`에 덮어쓴다.
  - `GET /v1/clans/{clanTag}/currentwar`: 진행 중이거나 막 끝난 일반 클랜전
  - `GET /v1/clans/{clanTag}/currentwar/leaguegroup`: 이번 시즌 리그전 그룹과 전투 태그 목록
  - `GET /v1/clanwarleagues/wars/{warTag}`: 리그전 전투 하나의 상세
- **끝난 클랜전(`state == "warEnded"`)만 저장한다.** 진행 중이면 다음 실행을 기다린다.
- 리그전 전투 응답에는 두 클랜이 `clan`과 `opponent`로 들어오는데, 우리 클랜이 어느 쪽인지 정해져 있지 않다. 태그를 비교해 우리 쪽을 찾는다. 우리 클랜이 참가하지 않은 전투(같은 그룹의 다른 클랜끼리의 전투)는 건너뛴다.
- 같은 클랜전을 두 번 저장하지 않는다. 파일 이름이 식별자 역할을 한다.
- 새로 저장한 파일이 없으면 아무것도 바꾸지 않고 종료한다.

왜 주기 실행이 필요한가: 일반 클랜전의 멤버별 공격 기록은 다음 클랜전 준비가 시작되는 순간 API에서 사라진다. 전적(war log) 엔드포인트에는 클랜 전체 결과만 있고 멤버별 별 수가 없다. 리그전 전투는 시즌 중에는 다시 조회할 수 있지만 시즌이 끝나면 전투 태그 목록을 알 수 없게 된다. 따라서 30분 주기 실행은 데이터 유실을 막는 안전망이고, 수동 버튼은 즉시 갱신용이다.

### 2.2 계산기 (scoring)

- `data/wars/*.json`, `data/clan.json`, `config/clan.yaml`만 읽는다. 외부 호출이 없는 순수 계산이다.
- 월별로 멤버당 공격 횟수, 미공격 횟수, 별 총합, 별 평균, 점수를 집계하고 커트라인과 30인 선발 명단을 만든다.
- 점수 규칙 문구는 이 모듈의 docstring과 상수 한 곳에만 정의하고, 렌더러가 그것을 읽어 페이지 상단에 표시한다. 코드와 화면의 규칙이 어긋나지 않게 하기 위함이다.
- 나중에 서버 방식으로 옮기더라도 이 모듈은 그대로 재사용한다.

### 2.3 렌더러 (render)

- 계산 결과로 정적 HTML을 만들어 `site/`에 쓴다. Jinja2 템플릿을 쓰고, 자바스크립트는 넣지 않는다.
- 휴대폰 화면에서 표가 읽히도록 CSS를 작성한다.

## 3. 데이터 형식

### 3.1 클랜전 파일 (`data/wars/`)

클랜전 하나당 JSON 파일 하나. 파일 이름은 `{종료시각 UTC}_{종류}_{상대클랜태그}.json` 형식이다. 예: `2026-09-05T14-30-00Z_regular_2PP0JJ8L.json`. 태그의 `#`은 파일 이름에서 뺀다.

API 응답을 그대로 저장하지 않고 필요한 것만 정리한다.

```json
{
  "war_type": "regular",            // "regular" | "cwl"
  "start_time": "2026-09-04T14:30:00Z",
  "end_time": "2026-09-05T14:30:00Z",
  "team_size": 30,
  "attacks_per_member": 2,          // regular 2, cwl 1
  "opponent": {"tag": "#2PP0JJ8L", "name": "상대 클랜"},
  "members": [
    {
      "tag": "#ABC123",
      "name": "도토리",
      "townhall": 18,
      "attacks": [{"order": 1, "stars": 3}, {"order": 2, "stars": 2}]
    }
  ]
}
```

- `members`에는 우리 클랜 참가 멤버만 넣는다. 명단에 있지만 공격하지 않은 멤버는 `attacks`가 빈 배열이다.
- `stars`는 그 공격에서 딴 별 수(0~3)다. API의 `attacks[].stars` 값을 쓴다.
- 파일은 한 번 저장되면 수정하지 않는다.

### 3.2 클랜원 스냅샷 (`data/clan.json`)

매 실행마다 덮어쓰는 현재 클랜원 목록이다. 클랜전 파일과 달리 이력은 남기지 않는다(git 이력으로는 남는다).

```json
{
  "fetched_at": "2026-09-07T09:00:00Z",
  "name": "미니언즈",
  "tag": "#2C8L822LQ",
  "members": [
    {"tag": "#ABC123", "name": "도토리", "role": "coLeader", "townhall": 18,
     "trophies": 5200, "donations": 1200, "donations_received": 900}
  ]
}
```

`role`은 API 값(`leader`, `coLeader`, `admin`, `member`)을 그대로 두고, 화면에서 대표/공동 대표/장로/멤버로 바꿔 보여 준다.

### 3.3 관리자 설정 파일 (`config/clan.yaml`)

```yaml
clan_tag: "#XXXXXXX"
elite:                      # 정예 멤버 (플레이어 태그)
  - "#AAAAAAA"
alts:                       # 부캐 (정예 불가)
  - "#BBBBBBB"
excluded:                   # 선발에서 제외
  - "#CCCCCCC"
warnings:                   # 경고 횟수 (표시용)
  "#DDDDDDD": 1
```

- 관리자는 GitHub 웹에서 이 파일을 고치고 저장한다. 다음 실행 때 반영된다.
- 태그는 `#`으로 시작하고 영문 대문자와 숫자로 이루어져야 한다. 형식이 틀리면 계산 단계에서 어느 항목이 잘못됐는지 알려주고 멈춘다.

### 3.4 멤버 식별

멤버는 닉네임이 아니라 **플레이어 태그**로 식별한다. 닉네임은 바뀔 수 있지만 태그는 영구적이다. 화면에는 그 멤버가 참가한 가장 최근 클랜전에 기록된 닉네임과 홀 레벨을 보여 준다. 클랜을 떠난 멤버도 참가했던 달의 표에는 그대로 남는다.

## 4. 점수 계산 규칙

엑셀의 "2026.9~ 적용" 규칙을 그대로 옮긴 것이다. 이미지의 실제 숫자로 검산했다.

### 4.1 월 귀속

클랜전이 어느 달에 속하는지는 **종료 시각을 한국 시간(Asia/Seoul)으로 바꾼 날짜의 달**로 정한다. 8월 31일에 시작해 9월 1일에 끝난 클랜전은 9월에 들어간다.

### 4.2 공격 기회와 점수

- 클랜전 명단에 들어간 멤버는 일반 클랜전 2회, 리그전 1회의 공격 기회를 얻는다. 명단에 없으면 기회가 없다(엑셀의 빈칸).
- 공격 1회 점수 = 기본 5점 + 그 공격의 별 수 (최대 8점). 미공격 = 0점.
- 월 집계:
  - 공격 기회 = Σ(참가한 클랜전의 멤버당 공격 횟수)
  - 공격 횟수 = 실제로 한 공격 수
  - 미공격 횟수 = 공격 기회 − 공격 횟수
  - 별 총합 = Σ(각 공격의 별 수)
  - 별 평균 = 별 총합 ÷ 공격 기회
  - **점수 = (5 × 공격 횟수 + 별 총합) ÷ (8 × 공격 기회) × 100**

검산 예 (이미지의 8월 표):

| 닉네임 | 공격 | 미공격 | 별 총합 | 점수 |
|---|---|---|---|---|
| 도토리 | 27 | 0 | 81 | 100.0 |
| Taimanin | 27 | 0 | 80 | 99.5 |
| 정사과 | 25 | 2 | 75 | 92.6 |
| 군방 | 23 | 4 | 62 | 81.9 |
| 빼빼 | 70 | 2 | 170 | 90.28 |

### 4.3 커트라인

그 달 **공격 횟수 10회 이상** 이고 **점수 70점 이상**. 정예 멤버에게도 똑같이 적용한다.

### 4.4 선발 순서 (총 30인)

1. 커트라인을 넘은 정예 멤버를 점수 높은 순으로 먼저 넣는다.
2. 남은 자리를 커트라인을 넘은 일반 멤버 중 점수 높은 순으로 채워 총 30명까지 뽑는다.
3. 동점이면 별 총합이 많은 쪽, 그다음 공격 횟수가 많은 쪽, 그다음 닉네임 순으로 위에 둔다.

### 4.5 부캐, 제외, 경고

- `alts`에 등록된 태그는 `elite`에 있어도 정예로 취급하지 않는다. 일반 멤버로서 점수 경쟁은 한다.
- `excluded`에 등록된 멤버는 표에는 보이되 선발되지 않는다.
- `warnings`는 표에 표시만 하고 점수에 영향을 주지 않는다. 엑셀 규칙에 감점 규정이 없기 때문이다.

### 4.6 표시 형식

점수는 소수 첫째 자리, 별 평균은 소수 둘째 자리까지 표시한다. 순위를 매길 때는 반올림 전 값을 쓴다.

## 5. 웹 페이지

GitHub Pages 주소는 `https://circlebro.github.io/coc-pointer/`이다. 주소를 아는 사람은 누구나 볼 수 있다.

### 5.1 첫 페이지 (`/`)

- 상단: 선발 규칙 요약 (계산 모듈의 규칙 문구를 그대로 표시)
- 이번 달 최종 선발 명단: 순위, 닉네임, 홀 레벨, 공격, 미공격, 별 평균, 점수, 선발 근거(정예/선발)
- 다른 달로 가는 링크 목록
- 하단: 마지막 갱신 시각, 이번 달에 반영된 클랜전 수

### 5.2 월별 페이지 (`/2026-09/`)

엑셀의 세 표를 순서대로 보여 준다.

1. **최종 선발 명단**: 첫 페이지와 같은 표
2. **월 점수표**: 커트라인 미달 멤버까지 전원. 정예는 색으로 구분, 커트라인 미달은 흐리게, 제외 멤버는 취소선. 부캐 여부와 경고 횟수는 별도 열.
3. **클랜전별 기록표**: 세로는 멤버, 가로는 클랜전(날짜, 종류, 상대 클랜명). 칸에는 공격별 별 수를 `3/2`처럼 표시. 미공격은 `x`, 미참가는 빈칸.

모든 표는 점수 순으로 미리 정렬한다. 정렬 버튼은 없다. 그 달에 클랜전이 하나도 없으면 "기록 없음"을 표시한다.

### 5.3 클랜원 목록 페이지 (`/members/`)

`data/clan.json`을 표로 보여 준다. 열: 닉네임, **플레이어 태그**, 역할, 홀 레벨, 트로피, 기부, 수령. 설정 파일에 등록된 정예·부캐·제외 여부도 열로 표시해서, 관리자가 설정이 제대로 반영됐는지 한눈에 볼 수 있게 한다. 역할 순(대표 → 공동 대표 → 장로 → 멤버), 같은 역할 안에서는 트로피 순으로 정렬한다. 첫 페이지에서 이 페이지로 가는 링크를 둔다.

## 6. 자동 실행 (GitHub Actions)

`.github/workflows/collect.yml` 하나가 두 계기로 실행된다.

- `schedule`: 30분마다
- `workflow_dispatch`: Actions 탭의 "Run workflow" 버튼

실행 순서:

1. Python 3.14와 `uv`를 준비하고 `uv sync`로 의존성을 설치한다.
2. `uv run coc-pointer collect`: 새 클랜전을 `data/wars/`에 저장한다.
3. `uv run coc-pointer build`: 점수를 계산해 `site/`에 HTML을 만든다.
4. `data/`에 새 파일이 있으면 커밋하고 푸시한다.
5. `site/`를 GitHub Pages에 배포한다.

API 토큰은 저장소 Secrets에 `COC_API_TOKEN`으로 넣고, 환경 변수로만 읽는다. 코드나 파일에 적지 않는다.

알아 둘 점: GitHub는 저장소에 60일간 커밋이 없으면 예약 실행을 자동으로 끈다. 수집기가 새 클랜전마다 커밋하므로 클랜전이 계속되는 한 문제없다.

## 7. 오류 처리

- API 응답 실패, 토큰 오류: 수집 단계를 실패로 끝낸다. 저장된 데이터는 건드리지 않으므로 기존 페이지가 유지된다. GitHub가 저장소 주인에게 실패 알림 메일을 보낸다.
- 전적 비공개(`403`): 명확한 메시지("클랜 전적을 공개로 설정해 주세요")를 남기고 실패한다.
- 클랜전 진행 중: 저장하지 않고 정상 종료한다.
- 설정 파일 오류: 잘못된 항목을 지목하고 계산 단계에서 멈춘다.
- 리그전이 아닌 시기의 `leaguegroup` 404: 정상으로 취급하고 넘어간다.

## 8. 모듈 구성

```
src/coc_pointer/
  __init__.py      # 패키지, CLI 진입점
  cli.py           # `collect`, `build` 명령
  api.py           # CoC API 클라이언트 (httpx, 프록시 주소, 토큰)
  collect.py       # 클랜전 수집과 파일 저장
  models.py        # War, WarMember, Attack, MonthlyRow 같은 자료형 (dataclass)
  config.py        # config/clan.yaml 읽기와 검증
  scoring.py       # 점수·커트라인·선발 계산 (순수 함수, 규칙 docstring 포함)
  render.py        # Jinja2로 site/ 생성
  templates/       # HTML 템플릿과 CSS
```

추가 의존성: `httpx`(API 호출), `pyyaml`(설정), `jinja2`(템플릿).

- **점수 공식**: 4.2절의 검산표 5명분을 정답으로 하는 테스트. 코드가 엑셀과 다르게 계산하면 바로 잡힌다.

- **수집기**: 실제 API 응답을 흉내 낸 샘플 JSON으로 파싱과 파일 이름 생성, 중복 저장 방지를 검증한다. 테스트 중 실제 API를 부르지 않는다.
- **렌더러**: 생성된 HTML에 기대한 닉네임, 점수, 규칙 문구가 들어 있는지 확인한다. 클랜원 목록 페이지에 태그와 역할이 표시되는지 확인한다.
